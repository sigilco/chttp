# Release v0.2.0 learnings (2026-10-14)

Board: sigilco/chttp#39 (closed). Release: https://github.com/sigilco/chttp/releases/tag/v0.2.0. Procedure lives in `RELEASING.md`; this note is the why.

## Timeline

- Dry run of `pnpm version -r` in a throwaway worktree found the blocker before any tag: `ERR_PNPM_VERSIONING_INTERNAL_RANGE` on literal peer ranges.
- Eight PRs (#40 to #48) landed the cleanup, peer ranges, license, CONTRIBUTING, changelog generator, three stage workflow and the release PR.
- First tag run: `verify` green, `publish` red at `pnpm -r build` (examples need scriptc exec bits). Nothing published.
- Fixed in #48, moved the tag onto the fix commit, second run published all seven packages.

## Findings

1. pnpm native versioning requires `workspace:^` for internal peer ranges, and pnpm rewrites them only on `pnpm pack` or `pnpm publish`. Releases must never go through npm.
2. `versioning.ignore` takes exact names. A `chttp-*` glob silently did nothing.
3. A release tag need not be an ancestor of main. `git describe` picked v0.0.1 as the previous tag because v0.1.0 sits on a pre-squash commit. Sort tags by version instead.
4. Jobs do not share setup. `verify` had the exec-bit `chmod`, `publish` did not, and `pnpm -r build` also compiled the scriptc examples. Build only what the job ships.
5. A tag runs the workflow file from the tagged commit, so fixing a failed release workflow means moving the tag. Safe only before any publish.
6. New npm package names read as 404 for about five minutes after `Published package` (observed 23:52 publish, visible 23:57). Treat as lag, not failure.
7. The `already on npm` skip uses `npm view`, which has the same lag. A rerun inside that window could try to republish and hit npm's publish-over rejection. Rerun after the window or check the registry first.

## Open follow-ups

- `pnpm change check` validates intents and versions but does not fail a PR that touches `packages/*` without an intent.
- npm trusted publishing (OIDC) and `--provenance`: the log shows `Skipped OIDC ... 404`, publishing used `NPM_TOKEN`. Needs npm side setup by the owner.
